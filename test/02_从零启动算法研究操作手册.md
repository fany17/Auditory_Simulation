# 1. 手册定位与使用边界

## 1.1 这本手册解决什么问题

本手册把“我想研究一个算法”转换为一条可以检查、可以失败、可以复现、可以审核的工作路径。它教读者：

1. 怎样用不同详细程度的 Prompt 表达研究目标；
2. 怎样区分 TA 计算神经仿真路线和 TB 人工智能时变模型路线；
3. 怎样由规划者形成未来任务书，而不是一上来生成大量代码；
4. 怎样检查环境、代码、测试、实验、图和报告；
5. 怎样使用 Git 或纯本地 Markdown 文件保存过程；
6. 怎样判断结果应被接受、局部返工、完整重做还是回滚；
7. 怎样保留阴性结果，并让下一轮任务建立在可靠证据上。

本文不是“照抄命令即可得到科学结论”的教程。算法能够运行，只说明工程链路走通；只有输入、对照、测试、评价、证据边界和重复性同时合格，才可能形成有限的研究结论。

## 1.2 与项目总纲的关系

项目总纲规定本项目的长期目标：

> 本项目要建立一套可持续扩展的“听觉时变信息处理实验平台”，从计算神经仿真和人工智能基础算子两个方向，研究听觉时间信息如何形成、传递、转换、丢失、被读取和被调控。

本手册不改变这一定位。它只把总纲转化为初学者可以遵循的操作方法。遇到冲突时：

1. 科学目标和项目边界以项目总纲为准；
2. 当前一轮要做什么，以未来经人工确认的 `CURRENT_TASK.md` 为准；

4. 是否接受结果，以审核报告和人工决定为准；
5. 本手册不能代替上述任何一项证据。

## 1.4 读者应学会区分的五类陈述

| 类别 | 含义 | 示例 | 写作要求 |
|---|---|---|---|
| 项目既定目标 | 已由总纲确定的研究方向 | TA001 研究听神经样 spike 最小闭环 | 可明确表述为项目计划 |
| 外部事实 | 由论文、官方文档或生理知识支持 | spike 是离散动作电位事件 | 需要可靠来源，不能凭模型输出反推 |

# 2. 项目的两个研究方向

## 2.1 为什么必须分成两条路线

两条路线都研究“时间信息”，但研究对象和可支持的结论不同：

- **路线 A（TA）**研究真实神经系统的可计算近似：声音怎样变成发放率、spike、神经群体活动和 LFP 近似，以及下游怎样读取这些状态。
- **路线 B（TB）**研究人工模型的计算结构：卷积、循环、注意力、状态空间、池化和分块等算子怎样保留或丢失时间信息。

二者可以共享刺激、时间标签、probe 和下游 decoder，但不能把人工模型某层直接叫作某脑区，也不能把简化神经仿真当作完整人脑。两条路线应先独立闭环，达到共同接口条件后再汇合。

## 2.2 路线 A：TA 计算神经与脑机接口仿真

### 2.2.1 路线 A 研究什么

路线 A 关注以下对象及其转换关系：

```text
声音
→ 频率通道
→ 换能、压缩与适应
→ firing rate
→ spike
→ 神经群体
→ LFP或其他宏观状态近似
→ 下游decoder
→ 输入或中间状态调控
→ 下游变化
```

- **声音 waveform（波形）**：随时间变化的声压或数字振幅序列。
- **firing rate（发放率）**：单位时间内预期或实际出现多少次 spike，常用 spikes/s 或 Hz 表示。瞬时发放率是随时间变化的连续量。
- **spike（神经脉冲）**：神经元动作电位事件。在算法里通常记录为一组离散时间点，而不是普通连续音频波形。
- **spike train**：一个神经元在一段时间内的全部 spike 时间序列。
- **神经群体**：多个神经元或多个模拟单元的集合；每个单元可有不同频率偏好、阈值、噪声或延迟。
- **LFP（local field potential，局部场电位）**：电极附近大量神经元跨膜和突触电流经组织传导形成的低频电势。它是连续信号，来源和尺度都与 spike 不同。
- **decoder（解码器）**：从中间状态预测输入属性或下游目标的算法。为判断中间状态是否含有可用信息，最初通常使用低容量、可解释的 decoder。
- **调控**：有目的地改变输入、spike 模式、群体同步、延迟或宏观状态，观察下游读取是否按预期改变。

### 2.2.2 spike 与 LFP 为什么不是同一种信号

spike 是单个或少量神经元的快速、离散事件；LFP 是大量细胞电流经空间叠加和组织传导形成的连续电位。两者可以相关，但不能用“把 spike 画成平滑曲线”就声称得到了真实 LFP。

如果未来从 spike 群体构造一个连续信号，必须写作 **LFP proxy（LFP 近似或代理）**，并明确：

- 使用了 spike 卷积、突触电流、膜电流还是其他 forward assumption；
- 核函数、符号、时间常数、几何权重和采样率；
- 该近似能回答什么，不能回答什么；
- 它不能直接等同于临床电极记录。

### 2.2.3 phase locking 与 adaptation

- **phase locking（相位锁定）**：spike 倾向在周期刺激的某个相位出现。例如同一 AM 周期的相似位置反复发放。常用 vector strength 量化；高值说明事件相位集中，但仍需考虑 spike 数和统计显著性。
- **adaptation（适应）**：刺激开始时反应较强，持续刺激下反应减弱或状态逐渐改变。工程模型可用一个或多个时间常数近似，但这只是对生理现象的简化，不代表所有细胞机制。

### 2.2.4 为什么从听神经和 TA001 开始

听神经位于声音外周换能之后，是从声音到离散神经事件的较早接口。先从这里开始有四个好处：

1. 输入可控：可以生成纯音、AM、节拍、jitter 和 omission；
2. 输出可解释：能直接检查频率通道、发放率和 spike timing；
3. 错误可定位：可逐步检查 filterbank、压缩、适应和 spike generation；
4. 依赖较少：TA001 可以只用 CPU，先做 rate，再做 spike，先单通道，再做群体。

TA001 只建立“输入→中间状态→读取→扰动→变化”的最小闭环。它不复刻完整耳蜗、所有听觉核团或人脑，也不能独立支持临床结论。简化模型的价值是提供透明、可测试的起点，而不是证明“人脑就是这样工作”。

## 2.3 路线 B：TB 人工智能基础算子与时变模型

### 2.3.1 路线 B 研究什么

路线 B 比较传统信号处理、简单时序模型和公开预训练模型，观察时间信息在不同模块和层中怎样变化。常见模型包括：

- **CNN（卷积神经网络）**：用局部卷积核提取模式；时间 CNN 沿时间轴滑动。
- **TCN（Temporal Convolutional Network）**：通常使用因果或膨胀卷积处理长时间序列。
- **RNN（循环神经网络）**：逐步更新隐藏状态；后续状态依赖之前输入。
- **GRU / LSTM**：带门控的 RNN 变体，用门控制信息保留、更新和遗忘。
- **Transformer**：用 attention 在多个时间位置之间建立联系。
- **Conformer**：常把卷积的局部模式与 Transformer 的上下文整合结合。
- **state-space model（状态空间模型，SSM）**：通过连续或离散状态更新表达长序列动力学；具体性质取决于实现，不能只凭类别名称判断流式能力。
- **预训练语音/音频模型**：在大规模语音或音频上预训练、可提取多层表示的公开模型；实际权重、许可证、接口和硬件必须逐项核验。

### 2.3.2 初学者必须理解的术语

- **模型层（layer）**：模型中的一个变换阶段。输入经过多个层逐步变成新的表示。层编号只表示位置，不表示脑区或功能名称。
- **特征（feature）/ embedding**：模型从输入计算出的数值表示。一个特征能被读取，不等于主任务实际使用它。
- **pooling（池化）**：把一段位置的值汇总，常用于降低分辨率。它可能提高稳健性，也可能模糊事件时间。
- **stride（步幅）**：卷积或窗口每次移动多少采样点或帧。stride 大于 1 常导致下采样。
- **感受野（receptive field）**：某个输出位置理论上或有效上能受多大范围输入影响。大感受野不等于所有细节无损保留。
- **attention（注意力）**：根据输入计算不同位置间的加权组合。它能整合远距离信息，但不自动保证精确相位、因果性或低延迟。
- **因果模型（causal model）**：某一时刻输出只使用当前和过去输入，不看未来。若预处理、归一化或窗口使用未来信息，整套系统仍不因果。
- **流式处理（streaming）**：数据持续到达时，模型按 chunk 或采样增量更新并维护状态。流式还需记录缓冲、look-ahead、首包延迟、持续延迟和状态重置。
- **probe（探针/读取器）**：冻结原模型后，用简单模型读取中间层中的目标信息。线性 probe 常用于降低“读取器自己重新学习任务”的风险。
- **ablation（消融）**：删除、替换或限制某个模块，并在公平对照下观察结果变化，用于检验该模块的作用。

### 2.3.3 为什么识别正确不等于保留精确时间信息

一个模型可能正确识别“这是一段鼓点”或“说了哪个词”，但已经把 onset 的毫秒级位置、载波 phase、微小 jitter 或某次 omission 的具体时刻压缩掉。内容分类只要求输出标签正确；时间研究要求检查中间层的输出更新率、事件对齐、phase error、跨条件可读性和因果延迟。

因此 TB001 不以最终准确率为唯一目标，而要逐层提取表示、训练低容量 probe，并记录每层时间分辨率、感受野、上下文和延迟。

### 2.3.4 为什么研究高速变化监测通路

项目有一个尚未证明的假设：

> 许多以内容识别或全局表征为主要目标的模型，在下采样、池化、分块、tokenization 和长上下文整合中，可能牺牲局部时间精度；并行的快速变化检测与慢速上下文整合，可能比单一时间尺度更适合连续输入。

高速通路的目标是专门检查 onset、phase shift、jitter 和 omission 等快速变化；慢速通路处理 tempo 和上下文。但它也可能放大噪声、增加计算量或破坏内容识别。只有参数量、训练预算、延迟和前端公平匹配的消融，才能判断高速通路是否真的有独立贡献。

# 3. 三种 Prompt 使用层级

## 3.1 层级一：最简单 Prompt

层级一只表达一句话：

> 我需要构建一个什么目标的算法。

它适合尚不知道模型、依赖、目录和指标的初学者。不要为了显得专业而一次填满所有技术细节；错误的细节会把任务带偏。下面六个 Prompt 可直接复制。

### 3.1.1 路线 A：听神经 spike

```text
我需要构建一个模拟听神经对不同声音产生spike响应的算法。
```

### 3.1.2 路线 A：LFP 与信息传递

```text
我需要构建一个模拟spike群体如何形成LFP，并分析信息如何继续向下游传递的算法。
```

### 3.1.3 路线 A：输入调控

```text
我需要构建一个研究改变声音节拍、相位和遗漏后，下游神经信息如何变化的算法。
```

### 3.1.4 路线 B：模型复现

```text
我需要构建一个复现现代语音或音频模型，并观察各层时间信息变化的算法。
```

### 3.1.5 路线 B：结构分析

```text
我需要构建一个通过删除和替换模型模块，分析哪些结构决定时间信息保留的算法。
```

### 3.1.6 路线 B：快速通路

```text
我需要构建一个增加高速变化监测通路的时序模型。
```

### 3.1.7 Codex 收到极简 Prompt 后的标准动作

收到极简 Prompt 后，Codex 不应立即生成大量代码。标准动作是：

1. 确认当前项目根目录；
2. 检查已有文件、代码、配置、数据说明和结果；
3. 阅读项目总纲；
4. 判断属于 TA 路线还是 TB 路线；
5. 用通俗语言复述科学目标；
6. 区分用户已明确内容与必要的最小默认假设；
7. 提出一个可测试的最小闭环；
8. 在被授权时形成一页初步任务书；
9. 列出输入、输出、测试、图和最小验收条件；
10. 等待人工确认，或严格按照既定授权进入执行；
11. 完成后报告实际文件、命令、测试、结果、偏差和未完成内容。

若 Codex 补充默认方案，应明确写成：

```text
用户已确定：研究不同声音引起的听神经样spike。
默认假设：第一轮使用合成声音、CPU和简化filterbank；这些假设可由用户修改。
尚未确定：具体Python版本、spike生成器、主要读取指标和验收阈值。
```

极简 Prompt 不授权擅自下载大模型、改变项目科学目标、创建 Git 仓库、提交代码或把默认假设写成用户决定。

## 3.2 层级二：由讨论 Agent 构建较复杂 Prompt

层级二的最终产物仍然是一份较完整的 Prompt，其逻辑形式仍是：

> 对什么目标，通过什么方法构建什么算法，设计一个用于回答什么问题的实验，执行后汇报指定内容。

但这不意味着初学者要亲自写完模型、依赖、目录、指标、测试和汇报要求。层级二应当使用一个**讨论与 Prompt 构建 Agent**：人类只给出简短研究意图，讨论 Agent 通过阅读项目材料、解释术语、提出必要问题和声明默认假设，最终代为生成可复制的正式执行 Prompt。

### 3.2.1 人类实际需要发送的 Prompt

通用起始 Prompt 应保持简短：

```text
我想研究【目标】。请作为本轮“讨论与Prompt构建Agent”，先阅读项目总纲和现有材料，用通俗语言与我确定最小科学问题、路线、baseline、输入输出、测试、图和结论边界，最后替我生成一份完整可复制的执行Prompt。本轮只讨论和构建Prompt，不实现、不安装、不下载、不运行。
```

更短的表达也可以：

```text
我想从TA001开始研究不同声音怎样产生听神经样spike。请先和我讨论，并替我构建后续执行Prompt；现在不要执行。
```

### 3.2.2 讨论 Agent 的标准工作

讨论 Agent 收到简短 Prompt 后，应：

1. 确认项目根目录并完整阅读总纲；
2. 只读审计已有代码、数据、环境说明和结果；
3. 判断属于 TA 还是 TB，并解释理由；
4. 把术语和科学问题翻译为初学者能理解的语言；
5. 区分“用户已确定”“建议默认值”“必须由人确认”“仍待核验”；
6. 只提出真正改变任务方向的少量问题；非阻塞事项给出可修改的默认方案；
7. 提出最小闭环、baseline、一个主要扰动、测试、图和报告边界；
8. 先给人类一页讨论摘要，等待确认或修订；
9. 确认后生成一份完整执行 Prompt；
10. 停止在 Prompt 生成阶段，不自动进入实现。

讨论 Agent 最终生成的执行 Prompt 至少包含：

```text
1. 项目路径、上位依据和授权边界；
2. 科学问题、TA/TB路线和建议任务编号；
3. 已确认事实、默认假设和待核验问题；
4. 统一输入、ground truth和数据切分；
5. 最小baseline、核心实现和一个主要扰动；
6. 输出、单元测试、图和机器审核；
7. 运行配置、日志、失败结果和可复现要求；
8. 完成后的汇报内容；
9. 能支持与不能支持的结论；
10. 禁止事项和停止条件。
```

因此，第 16 章中较复杂示例分为两部分：先给“人类发给讨论 Agent 的短 Prompt”，再给“讨论 Agent 应生成的执行 Prompt 要点或成品示例”。长 Prompt 是 Agent 的产物，不是要求初学者手工撰写的作业。

## 3.3 层级三：初始化两个独立 Agent 会话的完整工作流

层级三用于持续多轮、需要任务书、执行证据、独立审核和可回滚记录的长期工作。它不是“把一个很长 Prompt 发给一个 Agent”，而是初始化并维护两个职责分离的会话：

- **会话 A——Planner-Reviewer**：任务规划、科学设计、任务书、机器审核和下一轮决策；
- **会话 B——Executor**：环境核验、代码、实验、测试、图、日志和执行报告。

### 3.3.1 初始化顺序

必须先初始化会话 A，再初始化会话 B：

```text
人类阅读总纲和本手册
→ 新建会话A并发送Planner-Reviewer初始化Prompt
→ 会话A审计项目并生成项目规则与第一份任务书草案
→ 人工审核并批准任务书
→ 新建独立会话B并发送Executor初始化Prompt
→ 会话B从文件读取任务书和协议
→ 人工发送本轮执行指令
```

两个会话不依赖彼此的隐藏聊天上下文。`CURRENT_TASK.md`、`EXECUTION_REPORT.md`、`REVIEW_REPORT.md`、日志、图、Git diff 或文件 manifest 才是交接依据。

### 3.3.2 完整循环

1. 会话 A 完成项目材料审计；
2. 会话 A 建立总体项目结构和 TA/TB 编号；
3. 会话 A 建立角色、汇报、审核和回滚规则；
4. 会话 A 编写当前任务书；
5. 人工确认任务目标和授权范围；
6. 会话 B 读取任务书并核验环境；
7. 会话 B 实现最小版本；
8. 会话 B 先运行单元测试，再运行实验并绘图；
9. 会话 B 编写执行报告并停止；
10. 人工把执行状态交给会话 A；
11. 会话 A 检查实际文件、测试、图、指标及 diff/manifest；
12. 人工完成科学审核；
13. 会话 A 输出 `ACCEPT`、`REWORK`、`REDESIGN` 或 `ROLLBACK`；
14. 人工批准返工、回滚或下一轮任务后，相应会话才继续。

层级三不授权两个 Agent 自动无限接力，也不允许 Executor 自行修改任务书或宣布任务被接受。第 16 章提供会话 A 初始化、会话 B 初始化、任务生成、执行、审核、返工、重做、回滚和下一轮生成的成套 Prompt。

## 3.4 三层 Prompt 怎样选择

| 情况 | 推荐层级 | 人类实际需要写什么 | 预期产物 |
|---|---|---|---|
| 只有一个研究想法，希望系统先给方向 | 层级一 | 一句“我需要构建……” | 最小闭环建议和默认假设 |
| 希望形成一次可执行的专业 Prompt，但不懂全部技术细节 | 层级二 | 一句研究目标，并要求讨论 Agent 代为构建 Prompt | 经讨论确认的完整执行 Prompt |
| 需要长期多轮任务、执行、审核和回滚 | 层级三 | 分别发送会话 A 和会话 B 的初始化 Prompt | 文件化的双 Agent 工作流 |
| 只需要讨论，不允许修改文件 | 层级二 | 明确“只讨论和构建 Prompt” | 讨论摘要与 Prompt 草案 |
| 已有经人工批准的任务书 | 层级三执行阶段 | 初始化或唤醒 Executor 并指向任务书 | 实现、测试、图、日志和执行报告 |

# 4. TA/TB 任务编号体系

## 4.1 编号含义

- `TA` 表示计算神经与脑机接口仿真路线。
- `TB` 表示 AI 基础算子与时变模型路线。
- 三位数字表示任务系列中的唯一编号，不表示重要性、难度、优先级或日期。
- 编号一经使用，不因失败或停止而复用。
- 本手册解释编号规则，但本手册不是任何一个 TA/TB 任务。

## 4.2 TA 路线示例

```text
TA001  听神经spike最小闭环
TA002  听神经群体与population coding
TA003  spike群体到LFP近似
TA004  多层级神经信息传递
TA005  输入与中间状态调控
TA006  下游decoder和控制
TA007  自然输入与人工输入的功能比较
TA008  闭环调控或写入模拟
```

## 4.3 TB 路线示例

```text
TB001  代表性模型复现与逐层分析
TB002  模块替换与消融
TB003  高速变化监测通路
TB004  快慢多通路融合
TB005  动态采样与自适应时间常数
TB006  实时因果模型
TB007  实时评估与部署边界
TB008  跨音频、脑信号和其他时序任务迁移
```

## 4.4 任务依赖

每份未来任务书必须写出：

- `depends_on`：依赖哪些已审核任务；
- `uses_artifacts`：使用哪些代码、配置、数据或模型输出；
- `blocked_by`：哪些未解决问题会阻止执行；
- `entry_criteria`：开始前必须满足什么；
- `exit_criteria`：满足什么才可进入下一任务。

未通过审核的任务不能直接作为下一项任务的可靠基础。可以为了诊断而读取其失败输出，但必须标记为“未接受证据”，不能把它伪装成冻结 baseline。

默认依赖关系为：

```text
TA001 → TA002 → TA003/TA004 → TA005 → TA006 → TA007 → TA008
TB001 → TB002 → TB003 → TB004 → TB005 → TB006 → TB007 → TB008
```

允许有条件跳转，例如 TA004 可先使用 spike 群体而不依赖 LFP proxy；但必须在任务书和决策记录中解释为什么跳转、缺了什么、结论因此缩小到什么范围。

## 4.5 子实验与运行编号

推荐未来使用：

```text
任务：TA001
实验：TA001-EXP001
消融：TB002-ABL001
运行：TA001-EXP001-20260806T103000-seed001
```

不要只用 `final`、`new`、`best`、`latest` 命名结果。成功、失败、超时、发散和无效运行都保留唯一 `run_id`。

# 5. 两个未来 Agent 的角色

## 5.1 Agent A：Planner-Reviewer

Agent A 负责：

1. 阅读项目总纲；
2. 审计当前项目；
3. 判断当前属于 TA 还是 TB；
4. 把长期目标拆成可执行任务；
5. 编写任务书；
6. 定义测试；
7. 定义图；
8. 定义验收指标；
9. 定义失败条件；
10. 审核代码、日志、测试和图；
11. 判断 `ACCEPT`、`REWORK`、`REDESIGN` 或 `ROLLBACK`；
12. 在人工确认后更新下一轮任务。

Agent A 不得：

- 只给抽象建议；
- 用“继续完善”代替明确任务；
- 在没有证据时宣布完成；
- 把代码风格检查当作科学审核；
- 擅自扩大项目结论；
- 删除或忽略阴性结果；
- 未检查实际文件就只根据执行者文字汇报下结论；
- 一边审核一边偷偷改变原任务验收标准；
- 把未来愿景写成当前结果。

Agent A 的合格输出必须能回答：“下一步具体改哪个文件、运行什么检查、生成什么证据、达到什么才结束、失败后怎样处理？”

## 5.2 Agent B：Executor

Agent B 负责：

1. 阅读当前任务书；
2. 检查环境；
3. 实现代码；
4. 生成或获取输入；
5. 运行实验；
6. 编写测试；
7. 保存配置；
8. 保存日志；
9. 生成图；
10. 写执行报告；
11. 明确任务偏差；
12. 接受审核结果并按授权返工。

Agent B 不得：

- 在未读取任务书时直接编码；
- 擅自改变科学问题；
- 隐藏失败命令；
- 只保留最好的一次结果；
- 手工填写不存在的指标；
- 用手工绘制图冒充实验结果；
- 通过降低验收标准宣布成功；
- 在没有 baseline 时直接实现复杂新模型；
- 因为任务运行成功就自行宣布 `ACCEPT`；
- 未经授权下载大模型、重训大型模型、提交或推送 Git。

## 5.3 为什么规划审核与执行要分开

分开角色不是为了增加形式，而是为了避免执行者在遇到失败时悄悄更改问题、指标或验收标准。Agent B 提供事实和证据；Agent A 检查这些证据是否回答原问题；人工最终决定是否继续。

两个角色可以由不同 Agent 承担，也可以在不同时间由同一工具按不同 Prompt 承担，但必须保留清楚的角色切换、输入文件和输出文件。审核时不能只依赖执行阶段的上下文记忆。

# 6. 项目开始前的规划步骤

## 6.1 第一轮为什么不能直接大规模编码

没有审计就编码，常导致重复已有工作、写错目录、使用不可运行的模型、忽略许可证、制造数据泄漏，或得到无法回答科学问题的漂亮图。第一轮的目标是建立最小、可验证、可退出的任务。

## 6.2 Agent A 的十三步规划表

| 步骤 | 为什么做 | 需要打开或检查 | 应得到的结果 | 完成标志 | 常见错误 | 错误后处理 |
|---|---|---|---|---|---|---|
| 1. 找到项目根目录 | 防止在错误目录写文件 | 当前路径、上级目录、README、总纲 | 一个绝对根路径和边界说明 | 后续路径均相对同一根目录 | 把资料目录当代码仓库 | 停止写入，重新定位；不得擅自 Git 初始化 |
| 2. 列出已有文件 | 保护已有成果并发现真实状态 | 文件树、隐藏文件、大文件 | 文件清单和重点材料列表 | 能区分已有、缺失、生成物 | 只看顶层或凭记忆判断 | 扩大只读扫描范围并记录未访问边界 |
| 3. 阅读项目总纲 | 对齐科学目标和禁止事项 | `01_听觉时变信息处理项目总纲.md` | 目标、路线、最小闭环、边界摘要 | 能用自己的话解释 TA/TB | 只搜关键词不完整阅读 | 重新完整阅读，记录版本和路径 |
| 4. 判断代码和环境 | 知道能否复用及运行条件 | `src/`、`tests/`、配置、环境文件、日志 | “存在/不存在/待核验”清单 | 不虚构已有能力 | 看见文件名就认为可运行 | 只读核验入口、依赖和最近证据 |
| 5. 确认 TA/TB 路线 | 防止神经仿真和 AI 模型混写 | 科学问题、输入输出、总纲编号 | 路线选择及理由 | 主任务只有一个主路线 | 同时塞入两条路线所有目标 | 拆成独立任务，定义未来汇合点 |
| 6. 建立目录规划 | 使代码、配置、结果可追溯 | 总纲目录建议和现有结构 | 建议目录映射 | 每类文件有唯一职责 | 立即批量创建空目录 | 先写规划，只创建本任务需要的路径 |
| 7. 建立任务编号 | 保持任务、结果和报告一致 | TA/TB 编号表、历史记录 | 唯一 task id | 编号未复用且依赖明确 | 用日期或“final”代替任务号 | 在任务历史中分配新编号 |
| 8. 建立 Agent 交互规则 | 防止角色和权限混乱 | 协议模板、现有 `AGENTS.md`（若有） | 输入、输出、停止、权限规则 | A/B 责任和禁区明确 | 让 Agent 自动无限推进 | 增加人工确认点和轮次边界 |
| 9. 建立汇报规则 | 保证失败和偏差可见 | 报告模板、artifact 规范 | 必填报告字段 | 命令、配置、测试、阴性结果都有位置 | 只汇报“完成了” | 使用第 17 章模板重写 |
| 10. 建立机器审核规则 | 把可自动发现的错误前移 | 测试入口、静态检查、重绘命令 | 审核清单 | 每一验收项有证据路径 | 只检查代码风格 | 加入数据、数值、因果和 provenance 检查 |
| 11. 建立人工审核问题 | 防止技术通过替代科学判断 | 科学问题、图、结论、边界 | 12 项人工问题 | 人能判断结论是否越界 | 只看单一指标 | 检查对照、图、阴性结果和替代解释 |
| 12. 建立回滚方式 | 失败时保护可靠状态 | Git 状态或本地快照方案 | 回滚点、恢复步骤、保留清单 | 回滚目标和验证方法明确 | 先破坏后想备份 | 执行前创建可验证快照或记录基线 |
| 13. 写第一轮任务书 | 把目标变为有限动作 | 上述 12 步结果 | 一份可审阅任务书草案 | 输入、输出、测试、图、门槛、停止条件齐全 | 写成长期愿望清单 | 缩小到单一最小闭环后重新审阅 |

## 6.3 规划完成的最低证据

第一轮规划只有同时满足以下条件才算完成：

- 项目根目录已用绝对路径确认；
- 项目总纲已完整阅读；
- 当前已有和缺失内容分别列出；
- 主路线和唯一任务编号明确；
- 任务依赖、输入、输出、测试、图、资源边界明确；
- 成功、失败和停止条件明确；
- Git 或无 Git 的回滚方式明确；
- 人工已经读过任务书并确认目标；
- 尚未执行的大规模工作没有被写成“已完成”。

# 8. Git 与无 Git 两种协作方式

## 8.1 Git 基础术语

- **Git**：记录文件版本变化的工具。它能显示谁在什么时候改了什么，也能恢复到已记录状态。
- **repository（仓库）**：由 Git 管理的项目历史和当前文件集合。
- **working tree（工作区）**：当前磁盘上正在编辑、尚未全部记录为 commit 的文件。
- **diff（差异）**：两个状态之间逐行发生了什么变化。
- **commit（提交）**：对一组经过选择的文件变化制作一个带说明的版本记录。commit 不是上传，push 才通常涉及远端。
- **revert（反向提交）**：用一个新提交撤销某个旧提交的变化，同时保留历史。它不同于直接擦除历史。

Git 只能记录文件变化，不能证明代码科学正确。一个 commit 可以包含错误实验；一次通过测试也不能替代执行报告、图形审核和科学解释。

## 8.2 最基础的只读检查命令

以下命令只作为未来操作示例，本次没有执行：

```bash
git status
git diff
git diff --stat
git log --oneline -n 10
```

- `git status`：查看当前分支、已修改、未跟踪和暂存文件。
- `git diff`：查看尚未提交的逐行变化。
- `git diff --stat`：只查看各文件改动行数概览。
- `git log --oneline -n 10`：查看最近 10 个提交摘要。

运行前先确认当前位置真的是目标仓库。若命令报告 `not a git repository`，不要在科研资料原目录擅自运行 `git init`。应停止 Git 操作，报告当前状态；如确有 Git 试验需要，由人工授权在安全的 sibling 镜像目录中进行。

## 8.3 为什么实验前记录状态

实验前记录状态可以回答：

- 本轮开始前有哪些未提交修改；
- 哪些变化属于本任务，哪些属于他人；
- 当前 baseline 对应哪个版本；
- 新结果能否回到原代码重现；
- 发生污染或破坏时应恢复到哪里。

记录状态不等于允许提交或推送。是否 commit、commit 哪些文件、是否连接远端，都需要明确授权。不得把其他人的未提交修改一起打包。

## 8.4 为什么不能删除失败结果

失败结果可以揭示：

- 哪些参数导致数值发散；
- 哪个模型不适合当前硬件；
- 哪种图或指标暴露了数据泄漏；
- 下一轮怎样避免重复耗时；
- 阳性结果是否只是“只挑最好一次”。

如果结果体积很大，可以按保留策略迁移到归档或备份位置，但不能无记录永久删除。失败 run 的配置、随机种子、日志、决定和最小诊断图应保留。

# 9. 环境搭建操作说明

## 9.1 先理解什么是环境

软件环境是运行代码所需的操作系统、Python 解释器、包版本、驱动和硬件组合。环境一致可以减少“在我电脑上能运行”的问题，但环境建好不等于算法完成，更不等于实验结论正确。

本章命令全部是未来任务的示例。本次编写手册没有运行这些命令。

## 9.2 第一步：确认操作系统

Windows PowerShell 示例：

```powershell
[System.Environment]::OSVersion
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsArchitecture
```

```bash

cat /etc/os-release
```

用途：确定安装命令、路径格式和兼容性。完成标志是报告系统名称、版本和 64/32 位架构。常见错误是只写“Windows”或“Linux”而没有版本；应补充实际命令输出并保存到环境记录。

## 9.3 第二步：确认 Python

```powershell
python --version
python -c "import sys; print(sys.executable)"
py -0p
```

Linux 常用：

```bash
python3 --version
python3 -c "import sys; print(sys.executable)"
```

第一个命令查看版本，第二个查看实际解释器路径，Windows 的 `py -0p` 可列出 Python Launcher 发现的版本。若提示命令不存在，不要反复安装多个 Python；先确认机器权限、项目要求和安装来源。

## 9.4 第三步：确认是否有 Conda


Conda 是环境和包管理工具，但不是必需条件。若没有 Conda，可以使用 Python 自带的 `venv`。不要同时随意混用系统 Python、Conda 和多个 `venv`。

## 9.5 第四步：确认是否有 GPU

NVIDIA GPU 常用只读检查：

```bash
nvidia-smi
```

# 10. TA001 的初学者操作流程

## 10.1 最小科学问题

TA001 要回答：

> 不同频率、强度和时间结构的声音，如何在一个明确标注为近似的听神经模型中，转化为不同的瞬时发放率和 spike timing？

这里的“听神经样”表示工程近似。第一轮不要求完整耳蜗、不要求全部生理细节，也不要求 LFP。最低闭环是：

```text
可控声音
→ 频率通道
→ 换能、压缩和适应
→ 瞬时发放率
→ spike train
→ raster、PSTH和phase locking
→ 从spike读取一种输入属性
→ 改变一个参数
→ 观察可读性怎样变化
```

## 10.2 输入怎样从简单到复杂增加

第一批输入按下列顺序增加：

1. **silence**：检查自发率、数值漂移和假阳性；
2. **纯音**：改变 frequency，检查频率通道选择；
3. **强度对照**：在相同频率下改变 intensity；
4. **onset/持续刺激**：比较开始瞬间和持续阶段；
5. **AM**：改变调制率和相位；
6. **regular rhythm**：生成等时事件；
7. **jitter**：小幅扰动事件间隔；
8. **phase shift**：保持 rate 不变，只改变相位；
9. **omission**：在预期时刻省略一个事件。

每个合成刺激应保存 waveform、sample rate、duration、event onset/offset、frequency、intensity、modulation/beat 参数、omission 位置、jitter、seed 和 split。omission 的预期时刻与实际声学 onset 必须分开记录。

## 10.3 最简单模型

```text
waveform
→ filterbank
→ rectification
→ compression
→ adaptation
→ firing rate
→ spike generation
```

逐步解释：

- **filterbank（滤波器组）**：把声音分到多个频率通道。第一轮可先单通道验证，再扩展多通道。
- **rectification（整流）**：保留波形的一侧或能量包络，用作简化换能。
- **compression（压缩）**：输入增加时输出增幅变小，避免无限线性增长。
- **adaptation**：使 onset 响应与持续响应不同。
- **instantaneous firing rate**：每一时刻产生 spike 的期望速率，必须非负并有清楚单位。
- **spike generation**：根据 rate 生成离散 spike；Poisson 是一种工程基线，不等于真实听神经全部统计规律。

最稳妥的顺序是先画出每一步的中间量，确认 rate 正确，再加入随机 spike。如果 rate 已错误，加入 LIF 或复杂成熟模型只会使错误更难定位。

## 10.4 可选升级路径

| 升级 | 何时使用 | 新增问题 | 不应声称 |
|---|---|---|---|
| Poisson spike | rate 基线正确后 | 随机性怎样影响读取 | 真实听神经就是 Poisson |
| renewal/refractory | 需要不应期统计时 | 最短 ISI 和发放规律 | 已复刻全部离子通道 |
| LIF | 研究膜时间常数和阈值时 | 积分与阈值怎样改变 timing | LIF 等于听神经细胞 |
| Brian2 | 多神经元和状态方程需要框架时 | 单位、群体和突触管理 | 使用框架本身增加科学真实性 |
| NEURON | 明确需要生物物理形态/机制时 | 更详细电生理 | TA001 必须使用 NEURON |
| 历史 auditory-nerve model | 基础验证完成且来源可核验时 | 与成熟外周模型比较 | 模型复杂就自动更正确 |

历史模型开始前必须核验原始论文、官方或作者实现、版本、许可证、平台、采样率、输入标定、输出接口和资源要求。

## 10.5 必须生成和理解的输出

- **waveform**：输入时域波形，用于检查时长、振幅和事件时刻。
- **spectrogram（时频图）**：不同时间的频率能量，用于检查刺激是否生成正确。
- **frequency channel**：滤波器组各通道输出，用于检查频率选择。
- **firing-rate curve**：随时间变化的发放率，用于检查 onset、持续反应和适应。
- **spike raster**：横轴为时间、纵轴为神经元或重复 trial，每个点代表一个 spike。
- **PSTH（peri-stimulus time histogram）**：把相对刺激时刻的 spike 分箱统计，观察群体或多 trial 的时间响应。
- **ISI（inter-spike interval）**：相邻 spike 的时间间隔，用于检查不应期、burst 或异常时间。
- **vector strength**：spike 相对于周期刺激的相位集中程度，用于检查 phase locking。

每幅图必须标注任务编号、run id、刺激、单位、样本数/神经元数、参数和生成脚本。图不能只存截图；需要能够从配置和结果重绘。

## 10.6 初学者执行顺序与检查点

| 步骤 | 操作 | 应看到什么 | 完成标志 | 常见错误 | 处理 |
|---|---|---|---|---|---|
| 1 | 冻结刺激 schema | 每个刺激有 waveform 和 ground truth | 时间、频率、强度、seed 可追溯 | onset 标签与实际波形错位 | 先画波形并校验事件 |
| 2 | 建立单通道 filterbank | 目标频率附近响应较强 | 正弦扫频结果方向合理 | 未处理采样率/Nyquist | 增加频率合法性检查 |
| 3 | 加整流和压缩 | 输出非负或符合定义、无异常爆炸 | 输入增大时响应可解释 | 把数字振幅称作临床 dB SPL | 标记未校准强度代理 |
| 4 | 加 adaptation | onset 与持续段出现预期差异 | 时间常数和状态初值有记录 | 在 trial 间泄漏状态 | 每个 trial 明确重置 |
| 5 | 产生 firing rate | rate 非负、单位清楚 | silence 和强度对照合理 | rate 负值、NaN 或单位混乱 | 先修正 rate，不生成 spike |
| 6 | 生成 spike | spike 位于输入时长内 | 相同 seed 可复现 | 每 trial 复用相同随机流 | 记录并区分全局/运行 seed |
| 7 | 计算 raster/PSTH/ISI/VS | 指标与原始 spike 一致 | 图和表可由脚本重绘 | 分箱大小决定“结论” | 报告 bin sensitivity |
| 8 | 建立简单 decoder | held-out 数据高于机会水平 | split、null 和指标明确 | 随机切分相邻时间点 | 按刺激/seed 分组切分 |
| 9 | 扰动一个参数 | 输出和可读性曲线变化 | 其他参数保持冻结 | 一次改多个参数 | 恢复基线后单因素扫描 |
| 10 | 写有限结论 | 只描述模型中的因果变化 | 能说清不能支持什么 | 直接推广到人脑 | 改写为模型近似结论 |

## 10.7 最低测试

| 测试 | 检查内容 | 失败意味着什么 |
|---|---|---|
| deterministic seed | 相同配置和 seed 产生相同结果 | 随机状态未保存或运行不受控 |
| frequency response | 改变频率后通道响应改变 | filterbank、采样率或通道映射错误 |
| intensity response | 强度增加后平均 rate 按模型定义合理变化 | 压缩、标定或饱和异常 |
| silence test | silence 不产生异常高发放 | 偏置、自发率或数值漂移错误 |
| time bounds | 所有 spike 在 `[0, duration)` 内 | 时间轴、采样索引或单位错误 |
| invalid parameter | 负时长、越 Nyquist 频率等主动报错 | 输入验证不足 |
| finite numbers | 所有关键数组无 NaN/Inf | 数值不稳定或除零 |
| shape/unit test | channel、trial、time 维度和单位一致 | 下游指标可能全部错位 |
| reset test | trial/block 间状态按定义重置 | adaptation 或 LIF 状态泄漏 |

## 10.8 最小参数扰动

第一轮只选一个主要扰动，例如：

- adaptation time constant；
- firing threshold；
- 输入或发放 noise；
- membrane time constant；
- fixed delay 或 delay jitter。

扫描前冻结主要指标和范围。结果至少报告基线、多个合理参数点、失败点、随机种子变异和 decoder 可读性。只展示最好点不合格。

## 10.9 TA001 最小结论边界

合格表述示例：

> 在当前简化模型、刺激范围和随机种子下，增加 adaptation time constant 改变了持续阶段发放率，并使某项 held-out 输入读取指标下降。

不合格表述：

> 人脑听神经通过这个时间常数决定节拍感知。

TA001 最多说明模型中参数怎样影响 rate、spike 和可读性；是否对应真实生理机制，需要外部生理证据、成熟模型对照和更强实验。

# 11. TB001 的初学者操作流程

## 11.1 最小科学问题

TB001 要回答：

> 传统信号处理、简单时序模型和一个代表性公开预训练模型的不同阶段，分别保留了哪些快速与慢速时间信息？

最低闭环：

```text
统一可控声音
→ 传统特征
→ 简单时序模型
→ 一个代表性预训练模型
→ 各层时间序列表征
→ 简单probe
→ 时间结构扰动
→ 比较信息损失、因果性、延迟和资源
```

## 11.2 与 TA001 共享输入

TB001 尽量使用与 TA001 相同的 onset、frequency、AM、tempo、phase、jitter 和 omission 定义。这样未来能用相同 ground truth 比较两条路线。

共享不代表预处理完全相同。每个模型可能要求不同采样率、归一化和窗口；这些变换必须记录，并检查输入端是否已经丢失目标信息。

## 11.3 三类最低 baseline

1. **传统信号处理 baseline**：waveform、STFT、log-mel、onset detector 或 autocorrelation 中的合适组合；
2. **简单可训练时序 baseline**：一个小型 CNN、causal CNN、TCN、GRU 或 LSTM；
3. **代表性预训练模型**：从当前可获取、许可允许、硬件可运行且能提取中间层的公开模型中选择一个。

第一轮不同时运行多个大型模型，不重新预训练大型基础模型。传统 baseline 不是“落后对照”，而是帮助判断时间信息是在前端、下采样还是深层模块中丢失。

## 11.4 怎样选择代表性模型

开始前逐项填写核验表：

| 字段 | 必须确认 |
|---|---|
| 原始来源 | 原始论文 DOI、官方仓库或官方模型卡 |
| 权重 | 当前是否仍可下载、具体版本和哈希 |
| 许可证 | 代码和权重是否允许当前用途 |
| 输入 | 采样率、通道数、归一化、时长限制 |
| 中间层 | 是否有官方接口或可靠 hook，输出 shape |
| 时间信息 | 每层输出更新率、stride、窗口和上下文 |
| 因果/流式 | 是否真正 causal，look-ahead 和状态接口 |
| 资源 | CPU/GPU、显存、内存、下载大小、推理时间 |

无法确认的字段写“待核验”，不凭记忆填入。模型名相同也可能有多个实现或 checkpoint，必须固定精确版本。

## 11.5 怎样理解和提取中间层

### 11.5.1 hook 是什么

**hook（钩子）**是在模型前向计算经过某层时，临时读取该层输入或输出的机制。使用 hook 时应：

1. 先阅读模型结构和官方接口；
2. 明确 hook 的层名称和编号；
3. 记录输出 shape 的每一维含义；
4. 推理结束后移除 hook；
5. 避免保留计算图导致内存泄漏；
6. 用小输入检查 hook 没有改变模型输出。

如果模型官方提供 `output_hidden_states`，通常优先使用官方接口。

### 11.5.2 保存 embedding

embedding 文件至少关联：

- model id、checkpoint 和版本；
- layer id；
- stimulus id 和 split；
- 输入采样率与预处理；
- embedding shape、dtype；
- 每个时间 token 对应的物理时间；
- 是否含 padding、mask、look-ahead；
- 生成配置和代码版本。

不要一次保存全部刺激、全部层和高精度张量。先做容量估算，用少量样本检查；可按层、刺激或 batch 分块，必要时只保存预先定义的时间摘要。

### 11.5.3 记录时间分辨率并对齐事件

对每层记录：

- 输入一个采样点或帧代表多少秒；
- 输出相邻 token 间隔；
- 理论和实测 stride；
- 感受野或上下文范围；
- padding、窗口中心和边界规则；
- 输出时间戳对应窗口开始、中心还是结束；
- 因果系统的 look-ahead 和 algorithmic latency。

先用单个清楚 onset 的测试刺激，检查输入事件能否正确映射到每层时间轴。时间对齐错误会让所有 onset、phase 和 omission probe 失效。

## 11.6 Probe 入门

### 11.6.1 线性 probe 是什么

线性 probe 用线性回归、逻辑回归等低容量模型，从冻结的中间表示预测目标。其目的不是追求最高准确率，而是比较“同一种简单读取规则能否从不同层读出信息”。

### 11.6.2 为什么冻结原模型

冻结模型可避免 probe 训练反向改变原表示，使层间比较更接近“原表示已经包含什么”。如果对整个模型微调，性能变化可能来自重新学习，不再是纯读取分析。

### 11.6.3 为什么不用复杂 decoder

复杂 decoder 可能利用长上下文、非线性或数据捷径，重新构造原本不显式可读的信息。首轮使用低容量 probe，并匹配训练预算、输入维度和正则化。复杂 decoder 可作为后续上限，但不能替代简单 probe。

### 11.6.4 怎样切分训练和测试

- 按完整 stimulus、序列、speaker、block、seed 或 condition 分组；
- 相邻时间点不能随机分到训练和测试，因为它们高度相似；
- 超参数只在训练/验证集选择；
- 测试集只在流程冻结后评估；
- 用 label permutation、time shift、silence 或 matched-random 检查机会水平和捷径；
- onset/omission 等稀有事件报告类别不平衡处理。

## 11.7 评价指标

| 目标 | 指标示例 | 关键检查 |
|---|---|---|
| onset | F1、MAE | 容忍窗、重复检测、时间对齐 |
| tempo | MAE、相关或分类 | 测试 tempo 是否超出训练组合 |
| phase | circular error、vector-based score | 使用圆周统计，不把 359° 与 1° 当远 |
| omission | AUROC、AUPRC | 区分实际声能缺失与预期时刻 |
| latency | 首输出、持续延迟、algorithmic latency | 区分 GPU 耗时与 look-ahead |
| memory | 峰值内存/显存 | 包括缓存和 hidden state |
| causal | 未来输入扰动测试 | 输出不能因未来片段改变 |
| streaming consistency | offline 与 chunked 差异 | 相同可用上下文和边界条件 |

还应记录 parameter count、real-time factor、输出更新率和鲁棒性。不同模型的计算比较必须说明 batch size、设备、dtype、输入长度和预热条件。

## 11.8 最小扰动

可选择：

- 改变 stride；
- 改变或删除 pooling；
- 删除一层；
- 缩短 context；
- 输入 jitter；
- 输入 phase shift。

结构扰动要配公平 baseline。改变模块导致参数量变化时，应报告原始对照和参数量匹配对照；不能把“参数更多”写成“新结构更好”。

## 11.9 初学者执行顺序与检查点

| 步骤 | 操作 | 应看到什么 | 完成标志 | 常见错误 | 处理 |
|---|---|---|---|---|---|
| 1 | 冻结共享刺激和 split | ground truth 完整 | 与 TA001 时间变量可对齐 | 相邻帧随机切分 | 改为序列/seed 分组 |
| 2 | 跑传统 baseline | STFT/log-mel 时间轴可解释 | 至少一个目标高于 null | 前端已去相位却测试载波 phase | 更换前端或缩小结论 |
| 3 | 跑简单模型 | 训练/验证过程可追溯 | 有稳定可重现 baseline | 直接上复杂模型 | 先完成小模型 |
| 4 | 核验预训练模型 | 版本、许可、输入和资源齐全 | 一个模型可在当前硬件推理 | 同时下载多个大模型 | 只保留首选模型 |
| 5 | 提取逐层表示 | layer id、shape、时间戳明确 | 小样本可重复提取 | hook 顺序/层编号错 | 用已知输入逐层核对 |
| 6 | 训练线性 probe | train/val/test 和 null 清楚 | 层间差异跨 seed 可复现 | probe 泄漏未来或标签 | 重新设计 split/causal mask |
| 7 | 做因果/伪流式测试 | chunk、state、look-ahead 有记录 | offline/streaming 差异可解释 | 把 chunked 称作 causal | 做未来扰动测试 |
| 8 | 做一个扰动 | 只改变一个结构或输入因素 | 有匹配 baseline 和 failure case | 参数量/预算不匹配 | 补对照后再解释 |
| 9 | 记录资源 | 延迟、内存、设备和条件完整 | 别人能复现测量条件 | 只报单次最快耗时 | 预热并报告分布 |
| 10 | 写有限结论 | 区分可读性与使用 | 明确能/不能支持 | 命名“节律层/听觉皮层层” | 改为层编号和 probe 证据 |

## 11.10 TB001 最小结论边界

合格表述：

> 在冻结模型和当前 split 下，线性 probe 从第 N 层读取 onset 的误差低于第 M 层；输出 stride 增大后 phase probe 下降。该结果说明这些表示在当前条件下具有不同可读性。

不合格表述：

> 第 N 层就是快速变化层，模型像听觉皮层一样编码时间。

probe 可读性不等于显式编码、因果使用或脑区同源。需要消融、跨条件泛化和下游功能测试逐步增强证据。

# 12. 每轮任务的标准循环

## 12.1 标准流程

```text
Agent A写任务书
→ 人工确认目标
→ Agent B检查环境
→ Agent B实现最小版本
→ Agent B先运行测试
→ Agent B运行实验
→ Agent B生成图
→ Agent B写执行报告
→ Agent A机器审核
→ 人工检查图和结论
→ 接受、返工、重做或回滚
→ Agent A生成下一轮任务
```

## 12.2 每一步的输入、输出与失败处理

| 步骤 | 负责人 | 输入文件/证据 | 输出文件/证据 | 完成标准 | 失败怎么办 |
|---|---|---|---|---|---|
| 1. 写任务书 | Agent A | 总纲、ROADMAP、上一审核 | `CURRENT_TASK.md` 草案 | 单一科学问题、输入输出、测试图和门槛齐全 | 缩小范围，不能用愿景代替任务 |
| 2. 确认目标 | 人工 | 任务书草案 | 确认/修改决定 | 人能复述目标和不能做什么 | 未确认则不执行 |
| 3. 检查环境 | Agent B | 任务书、环境规范 | 环境记录、阻塞清单 | 解释器、硬件、磁盘、依赖边界清楚 | 记录错误；提出最小替代，不擅自升级 |
| 4. 最小实现 | Agent B | 确认后的任务书 | 最小代码、配置 | 最短链路可导入且接口明确 | 回到最小基线，停止扩展 |
| 5. 先运行测试 | Agent B | 代码、测试计划 | 测试日志 | 关键单元、shape、seed、数值检查通过 | 保存失败日志并修复；不能跳过 |
| 6. 运行实验 | Agent B | 冻结配置、通过测试的代码 | run 目录、原始日志和指标 | 运行与配置、代码、seed 可追溯 | 保留失败 run，判断 REWORK 或阻塞 |
| 7. 生成图 | Agent B | 真实结果文件 | 可重绘图和图索引 | 图与指标一致、单位和条件完整 | 修正绘图；不得手工伪造 |
| 8. 写执行报告 | Agent B | 实际文件、命令、测试、图 | `EXECUTION_REPORT.md` | 成功、失败、偏差和边界全记录 | 缺证据则状态保持未完成 |
| 9. 机器审核 | Agent A | 任务书、报告、实际文件、diff | 机器审核清单 | 必要测试重跑、artifact 可追溯 | 输出具体失败项和证据 |
| 10. 人工审核 | 人工 | 图、指标、审核报告、科学问题 | 人工决定或问题 | 结论范围与证据一致 | 要求解释、返工、重做或停止 |
| 11. 决策 | 人工 + Agent A | 全部证据 | ACCEPT/REWORK/REDESIGN/ROLLBACK | 理由、责任、下一动作记录 | 不使用模糊“继续完善” |
| 12. 下一轮 | Agent A | 接受结果或失败决定 | 下一任务草案/停止记录 | 依赖只指向已接受证据 | 依赖未通过则先修复或改路线 |

## 12.3 四种合法状态

- `ACCEPT`：当前任务的预定义目标和证据门槛已满足，可以作为后续依赖。
- `REWORK`：科学问题和总体设计仍有效，只需局部修正后重新审核。
- `REDESIGN`：问题理解、数据、baseline 或实验逻辑无效，需要新任务设计。
- `ROLLBACK`：当前修改破坏可靠状态或无法安全修复，应恢复到已验证基线。

Agent B 可以建议状态，但不能自行接受任务。Agent A 可以提出决定，人工保留最终判断。

# 14. 人工审核

## 14.1 人工必须回答的十二个问题

1. 这项任务实际回答了什么问题？
2. 输入、标签、对照和随机性是否清楚？
3. 图是否能让不了解代码的人直观看懂？
4. 模型行为是否与实际代码、配置和参数一致？
5. 有没有把工程近似说成生理事实？
6. 有没有把可解码性说成显式编码、因果使用或脑区等价？
7. 有没有遗漏阴性结果、失败 seed 或不稳定条件？
8. baseline 是否足够简单、有效且公平？
9. 改进是否只是参数量、计算量、look-ahead 或训练预算增加？
10. 下一步是否真的有必要，还是当前问题已得到 no-go 结论？
11. 应 `REWORK`、`REDESIGN`、`ROLLBACK` 还是停止该路线？
12. 当前结论能支持到什么范围，明确不能支持什么？

## 14.2 怎样看图而不被“漂亮”误导

人工审核图时检查：

- 原始或代表性输入是否可见；
- 坐标、单位、条件、样本数和随机种子是否说明；
- 对照是否与实验条件使用同一尺度；
- 均值之外是否显示变异；
- 是否只截取最好时间段；
- 图中的统计是否能回到指标表；
- 图是否由实际运行生成；
- 阴性条件和 failure case 是否有位置；
- 图注是否把相关、可读、泛化和因果区分开。

## 14.3 人工决定应怎样写

不写：

> 效果不错，继续完善。

应写：

```text
决定：REWORK
原因：TA001 的frequency decoder超过置换水平，但PSTH使用的bin未记录，且两个seed的结果不稳定。
必须修改：保存bin配置；增加预定义seed；重绘含置信区间的PSTH；重新生成执行报告。
不要求修改：filterbank结构和科学问题。
重新审核证据：测试日志、三seed指标表、重绘图、更新后的执行报告。
```

# 15. 返工、重做与回滚

## 15.1 局部返工（REWORK）

适用于：

- 图不清楚；
- 一个局部测试失败；
- 配置遗漏；
- 术语错误；
- 一项指标计算错误；
- 报告缺少路径；
- 任务目标和 baseline 仍然有效。

返工单必须列出：

- 保持不变的目标和文件；
- 允许修改的文件；
- 每个失败项的证据；
- 修复后重跑哪些测试和图；
- 是否需要重跑实验；
- 重新审核的门槛。

## 15.2 完整重做（REDESIGN）

适用于：

- 科学问题理解错误；
- 数据或标签错误；
- baseline 无效；
- 存在数据泄漏；
- 实验不能回答任务问题；
- 模型输出无法追溯；
- 图形并非由真实运行生成；
- 原任务验收指标无法区分提出的机制。

完整重做应关闭原任务状态、保留所有证据，再创建新的任务版本或新编号。不能直接覆盖原任务书，好像错误从未发生。

## 15.3 回滚（ROLLBACK）

适用于：

- 原有可靠代码被破坏；
- 环境被污染；
- 依赖冲突无法修复；
- 大规模文件误改；
- 新路线不可行且继续修改风险过高；
- 当前结果无法复现；
- 继续操作可能覆盖可靠 baseline。

回滚不是删除失败历史。必须保留：

- 失败任务编号；
- 失败日志；
- 失败图；
- 审核报告；
- 回滚原因；
- 回滚来源版本或快照；
- 回滚后的验证结果；
- 新任务的规避策略。

## 15.4 回滚安全原则

1. 先停止写入进程并确认精确目标；
2. 先记录当前失败状态，再恢复可靠状态；
3. Git 仓库优先使用可审计的安全操作，不擅自 `reset --hard`；
4. 科研资料原目录若不是典型仓库，不得直接初始化或做 Git 历史试验；
5. 需要删除的内容进入回收站；做不到则移动到备份目录；
6. 恢复后运行最小导入、关键测试和已知 baseline；
7. 只有验证通过，才把回滚标记为完成。

## 15.5 停止路线也是合法结果

如果公平 baseline 已达到目标上限、新结构优势在匹配后消失、目标信息在输入前端已经不可用，或多种合理模型均不能得到稳定结果，可以停止或转向。停止决定应说明：

- 已尝试哪些合理方案；
- 哪些证据排除了继续的必要性；
- 尚未解决的替代解释；
- 哪些 artifact 对其他任务仍有价值；
- 将来在什么新条件出现时可重新打开。

# 16. 三层 Prompt 示例库

## 16.1 使用说明

本章不再把所有示例平铺成一组同等级的长 Prompt，而是严格分为三部分：

1. **层级一——极简目标**：人类直接写一句目标；
2. **层级二——讨论 Agent 构建 Prompt**：人类发短 Prompt，讨论 Agent 生成详细执行 Prompt；
3. **层级三——双 Agent 完整工作流**：分别初始化 Planner-Reviewer 会话和 Executor 会话，通过文件完成多轮交接。

复制任何示例前，仍要核对绝对路径、授权边界和当前任务状态。示例中出现“执行”不代表本手册编写时已经执行；它只用于未来得到授权的具体任务。

若只想规划，应在 Prompt 开头加：


若已授权执行，也不能自动获得提交、推送、删除、大型下载、管理员操作或扩展科学目标的权限。

这一层不能把下面的长 Prompt 理解为“人类必须自己写出的内容”。正确顺序是：

```text

执行结束后汇报实际文件、环境、依赖、模型与权重来源、许可证、命令、测试、逐层指标、资源、图、阴性结果和失败case。明确“probe可读”不等于模型显式使用，不得预先把某层命名为节律层、语义层、快速层或脑区，不得自行提交或推送。
```

### 16.3.7 TB002 模块消融

**人类发给讨论 Agent：**

```text
我想研究pooling、stride、context或attention中哪个因素导致时间信息丢失。请先根据TB001证据帮我选一个主要因素和公平对照，再生成执行Prompt；现在不要改模型。
```

**讨论 Agent 确认 TB001 已通过审核并冻结主要消融后，生成的执行 Prompt 示例：**

```text

开始前阅读TB001任务书、执行报告、审核报告和实际代码，选择TB001已经显示明确层间变化的一项主要时间变量。若TB001存在数据泄漏、层时间轴错误或baseline未稳定，停止TB002并报告阻塞。

请选择一个主要机制因素，例如pooling、stride、context、attention或recurrence，并建立：
1. 冻结的原始baseline；
2. 删除或替换该模块的实验模型；
3. 参数量匹配baseline；
4. 如可行，计算量或延迟匹配baseline；
5. 相同数据、split、seed、训练预算、前端和因果约束。

请同时检查：
- onset、phase、jitter或omission等快速时间信息；
- tempo或内容信息；
- 训练稳定性、噪声鲁棒性、参数量、计算量、内存和延迟；
- 多seed结果和failure case；
- 改进是否由look-ahead、前端、参数或训练预算解释。

对每个消融保存配置、日志、checkpoint选择规则、逐层probe、下游指标和图。不得只展示最好模型或最好seed。生成一张完整消融表，包含原始、参数匹配、资源匹配和阴性结果。

执行结束后汇报实际文件、环境、命令、测试、消融表、主要效果、置信区间或seed变异、失败case、能支持的机制结论和不能支持的结论。若优势在公平匹配后消失，应如实给出no-go，不得自行提交或推送。
```

### 16.3.8 TB003 高速变化监测通路

**人类发给讨论 Agent：**

```text
我想尝试在主干外增加一个高速因果通路，专门检测onset、phase shift和omission。请先帮我判断证据是否足够、需要哪些对照，再生成执行Prompt；现在不要实现。
```

**讨论 Agent 确认 TB001/TB002 依赖、快慢任务和公平性后，生成的执行 Prompt 示例：**

```text

4. 随机门控或匹配参数的负控制。

- 慢速上下文是否保持；
- 门控是否比直接拼接和随机门控更有效；
- 噪声输入下高速通路是否放大假阳性；

- 参数量、FLOP、内存、训练预算和延迟匹配后优势是否保留；
- 单通路、快通路关闭和慢通路关闭的failure case。

保存所有配置、seed、日志、测试、指标、图和阴性结果。执行结束后汇报结构、对照、公平性、性能—延迟—噪声Pareto、机制证据和边界。不得仅凭总准确率宣布高速通路有效，不得自行提交或推送。
```

## 16.4 第三部分：层级三——双 Agent 完整工作流

这一部分不是把所有 Prompt 连续发给同一个会话。人类应创建两个相互独立的会话，并始终保持角色：

```text
会话A：Planner-Reviewer
  读取：总纲、手册、项目文件、执行报告和实际artifact
  写入：项目规则、路线图、任务书、审核报告和下一轮决定

会话B：Executor
  读取：任务书、协议、回滚计划和依赖artifact
  写入：代码、配置、测试、日志、图、运行记录和执行报告
```

初始化前，人类需要确认两个会话指向同一项目根目录，并明确当前目录能否写入、是否是 Git 仓库以及哪些动作需要另行授权。会话 A 先初始化；第一份任务书经人工批准后，才初始化会话 B。

### 16.4.1 会话 A 初始化：Planner-Reviewer

**人类在新建的会话 A 中发送以下 Prompt：**

```text
你现在是本项目独立的Agent A会话：Planner-Reviewer。你只承担规划与审核角色，不兼任Executor。请为当前听觉时变信息算法项目完成第一轮项目初始化规划。

本轮只负责材料审计、科学设计、工作规则和第一份任务书，不执行大规模编码，不安装环境，不下载数据或模型，不运行实验，不提交或推送Git。

必须执行：
1. 确认当前项目根目录和可访问边界；
2. 完整阅读doc/01_听觉时变信息处理项目总纲.md及相关规划、README、代码、配置、测试、日志和结果；
3. 区分已确认目标、外部事实、工程建议、研究假设和未来愿景；
4. 审计项目当前实际存在和缺失的内容，不虚构环境、数据、模型或结果；
5. 判断第一项工作属于TA还是TB，并说明理由；
6. 建立总体项目结构规划和TA/TB任务依赖；
7. 阅读并在获得授权时修订doc/PROJECT_CHARTER.md；
8. 创建coordination/ROADMAP.md；
9. 创建coordination/AGENT_PROTOCOL.md；
10. 确定当前唯一TA/TB任务编号；
11. 创建第一份coordination/CURRENT_TASK.md；
12. 在任务书中定义输入、输出、baseline、单元测试、机器审核、必须生成的图、验收指标、失败条件、停止条件和回滚方式；
13. 定义人工审核至少需要回答的科学问题；
14. 列出所有待核验模型、许可证、硬件和数据问题；
15. 完成后等待人工确认，不立即进入大规模编码。

PROJECT_CHARTER不得替代项目总纲；CURRENT_TASK必须是一个最小闭环，不能写成长远愿望列表；AGENT_PROTOCOL必须明确Agent A与Agent B的读写范围、禁止事项、报告格式和人工确认点。

完成后只汇报实际创建或修改的文件、审计结果、当前任务编号、依赖、验收条件、待确认问题和未执行事项。若当前目录不是典型Git仓库，不得在原科研资料目录初始化Git；只报告状态。
```

### 16.4.2 会话 A 后续 Prompt：生成 TA 任务书

以下 Prompt 发给已经初始化的会话 A：

```text
你是Agent A：Planner-Reviewer。请基于项目总纲、ROADMAP、TASK_HISTORY、上一轮执行与审核证据，为下一项TA路线工作编写一份可执行任务书。

开始前必须检查实际文件，确认所有depends_on任务均已ACCEPT。若依赖未通过，停止生成后续可靠任务，改为提出修复或重设计建议。

任务书必须写入未来约定的coordination/CURRENT_TASK.md，并包含：
- 任务编号、名称、路线、版本和状态；
- 单一科学问题及生物解释边界；
- 已接受依赖和具体artifact路径；
- 输入刺激、ground truth、采样率、单位和seed；

所有生理事实、模型近似和工程假设分开写。若任务涉及LFP，必须称为LFP proxy并写明forward assumption。任务范围应能形成“输入→仿真→中间状态→下游读取→参数扰动→输出变化”的闭环。

完成后仅汇报任务书路径、编号、目标、依赖、最低交付、验收门槛和待人工确认项，不执行代码或实验。
```

### 16.4.3 会话 A 后续 Prompt：生成 TB 任务书

以下 Prompt 发给已经初始化的会话 A：

```text
你是Agent A：Planner-Reviewer。请基于项目总纲、ROADMAP、TASK_HISTORY、上一轮执行与审核证据，为下一项TB路线工作编写一份可执行任务书。

开始前检查实际文件，确认依赖任务已经ACCEPT。若TB001逐层时间轴、probe split或baseline仍不可靠，不得直接进入TB002/TB003。

任务书必须写入未来约定的coordination/CURRENT_TASK.md，并包含：

```

### 16.4.4 会话 B 初始化：Executor

第一份 `CURRENT_TASK.md` 经人工批准后，新建独立会话 B，并发送：


### 16.4.5 会话 B 后续 Prompt：执行当前任务

### 16.4.7 会话 A 后续 Prompt：独立审核


### 16.4.8 会话 B 后续 Prompt：局部返工

只有会话 A 的审核结果为 `REWORK` 且人工批准返工范围后，才把以下 Prompt 发给会话 B：

```text
你是Agent B：Executor。Agent A对当前任务给出了REWORK。请只做审核报告明确列出的局部返工。

开始前完整阅读CURRENT_TASK.md、EXECUTION_REPORT.md和REVIEW_REPORT.md，列出：
- 保持不变的科学目标、baseline、split和验收门槛；
- 允许修改的文件和参数；
- 每个FAIL对应的证据；
- 必须重跑的测试、实验、指标和图；
- 不允许触碰的已有可靠artifact。

返工时不得扩大任务、改变科学问题、删除失败记录、覆盖原run或降低标准。为返工生成新的run id或报告版本，保留原失败证据。若修复一个问题导致需要改变任务设计，停止并请求REDESIGN，而不是继续改。

完成后更新执行报告，逐项说明原失败、修改、命令、新证据和剩余问题。建议重新审核，但不得自行标记ACCEPT，不得提交或推送。
```

### 16.4.9 会话 A 后续 Prompt：完整重做设计

审核结果为 `REDESIGN` 时，把以下 Prompt 发给会话 A，而不是让会话 B自行改变科学问题：

```text
你是Agent A：Planner-Reviewer。当前任务被判定为REDESIGN。请保留原任务书、代码、日志、图、执行报告和审核报告，不覆盖或删除历史，然后设计一个能够修复根本问题的新任务。

请先说明：
1. 原科学问题、数据、标签、baseline、split或实验逻辑中哪一项无效；
2. 为什么局部返工不能解决；
3. 原结果中哪些仍可作为诊断材料，哪些不能作为可靠证据；
4. 新设计怎样避免同一错误；
5. 是否沿用原任务编号的新版本，还是分配新编号，理由是什么。

新任务必须重新定义输入、对照、baseline、测试、图、验收、失败、停止和回滚条件；显式标记与原任务的差异。若涉及数据泄漏或标签错误，应从数据生成与split重新开始。

完成后输出新的任务书草案和决策记录，等待人工确认。不要立即执行代码、实验、提交或推送。
```

### 16.4.10 双会话回滚 Prompt

回滚必须先由会话 A 制定计划，再由人工批准，最后由会话 B 执行。不能把“规划回滚”和“动手恢复”塞进同一条自动运行指令。

**第一步：发给会话 A，生成回滚计划：**

```text
你是Agent A：Planner-Reviewer。当前审核建议为ROLLBACK。请先制定一份可人工审核的回滚计划，本轮不执行任何恢复或删除操作。

请：
1. 确认失败任务编号、回滚原因和建议恢复到的可靠基线；
2. 记录当前失败任务编号、Git状态或文件manifest；
3. 列出必须先停止的写入程序；
4. 列出需要保留的代码、配置、日志、图、报告和失败run；
5. 只读核验恢复来源的commit、tag、快照路径或SHA256 manifest；
6. 写明允许Agent B执行的逐步动作、精确源路径和目标路径；
7. 明确恢复后必须通过的最小导入、unit test和已知baseline；
8. 把计划写入ROLLBACK_PLAN或回滚记录草案，等待人工批准。

安全规则：
- 不使用未经授权的破坏性Git命令；
- 如果当前科研资料目录不是典型Git仓库，不得在原目录做Git历史试验；
- 不永久删除文件；需要移除时进入回收站，做不到则移动到带时间戳的备份目录；
- 不覆盖失败证据；
- 不把回滚写成任务成功。

若精确目标、可靠基线或恢复来源无法确认，输出BLOCKED，不猜测回滚目标。完成计划后停止，不通知Executor自动开始。
```

**第二步：人工批准计划后，发给会话 B 执行：**

```text
你是Agent B：Executor。人工已经批准当前ROLLBACK_PLAN。请先重新读取计划、审核报告和恢复来源，只执行计划中逐项授权的动作。

开始前再次确认精确源路径、目标路径、备份位置、Git或manifest状态以及所有写入程序已经停止。若任何路径、基线、授权或备份条件不一致，立即输出BLOCKED，不做猜测性操作。

执行时完整保留失败任务的代码、配置、日志、图、执行报告和审核报告；不永久删除文件，需要移除时进入回收站，做不到则移动到带时间戳的备份目录；不使用计划未授权的破坏性Git命令。

恢复后运行计划规定的最小导入、关键unit test和已知baseline，记录命令、退出码和结果。更新回滚记录，包含实际动作、保留位置、验证结果、未解决风险和下一任务规避策略。完成后停止，等待会话A复核，不自行宣布回滚已被接受，不提交或推送。
```

### 16.4.11 会话 A 后续 Prompt：下一轮任务生成

```text
你是Agent A：Planner-Reviewer。请根据当前任务的最终审核和人工决定，判断是否生成下一轮任务。

开始前阅读项目总纲、ROADMAP、TASK_HISTORY、当前任务书、执行报告、审核报告、人工决定和实际artifact。

先做决策：
- 如果当前状态不是ACCEPT，不能把其输出当可靠依赖；应生成REWORK、REDESIGN、ROLLBACK或停止建议。
- 如果当前状态是ACCEPT，检查下一任务的进入条件是否全部满足。
- 如果阴性结果已经排除当前路线的关键假设，可以生成停止/转向记录，而不是强行增加复杂度。

若允许生成下一任务：
1. 分配或确认唯一TA/TB编号；
2. 写明depends_on和具体artifact；
3. 只选择一个新的主要科学问题；
4. 说明为什么它必须建立在本轮结果之后；
5. 定义输入、baseline、一个主要扰动、测试、图、资源和验收；
6. 预注册go/no-go、停止和转向条件；
7. 明确哪些旧结论仍有效，哪些不应继承；
8. 等待人工确认后才执行。

完成后汇报是否建议继续、理由、下一编号、依赖、最小闭环、门槛和待确认问题。不要自动启动Executor，不提交或推送。
```

### 16.4.12 人类在两个会话之间的最短交接语句

任务书批准后，发给会话 B：

```text
会话A已经生成当前任务书，我已人工批准其目标和授权范围。请重新读取CURRENT_TASK.md并按“执行当前任务”Prompt开始；遇到越界或阻塞时停止，不自行修改任务书。
```

会话 B 完成执行报告后，发给会话 A：

```text
会话B已经完成本轮执行并写入EXECUTION_REPORT.md。请按“独立审核”Prompt检查实际文件、测试、图、指标以及Git diff或manifest，不要只复述执行者总结。
```

会话 A 给出决定后，人类必须明确选择：

```text
我已阅读REVIEW_REPORT.md，批准本轮状态为【ACCEPT / REWORK / REDESIGN / ROLLBACK】。只按该状态对应的Prompt继续，不启动其他任务。
```

这三条交接语句只负责让正确会话读取共享文件，不替代任务书、执行报告、审核报告或人工科学判断。

# 18. 初学者第一次启动的最小流程

## 18.1 十二步清单

下面十二步是第一次工作的最短安全顺序。每一步都必须看到证据再进入下一步。

### 第 1 步：找到项目根目录

- **应看到什么**：绝对路径、项目总纲所在位置、已有顶层文件。
- **应检查什么**：当前终端是否真的位于目标目录；是否存在同名副本。
- **常见错误**：在下载目录、上级资料目录或错误 clone 中工作。
- **错误处理**：停止写入，比较路径和总纲内容；无法确认时只读报告。
- **完成标志**：所有后续相对路径都能从唯一根目录解释。

### 第 2 步：阅读项目总纲

- **应看到什么**：项目定位、两条路线、三阶段、TA001/TB001、边界和待核验问题。
- **应检查什么**：文件路径、版本、是否完整阅读到末尾。
- **常见错误**：只读摘要或只搜索自己熟悉的术语。
- **错误处理**：重新完整阅读，写出五句话摘要和不能做的事项。
- **完成标志**：能解释本项目不是声音分类器，也不是脑区—模型层直接类比。

### 第 3 步：选择 TA 或 TB 路线

- **应看到什么**：主科学问题只属于一个主要路线。
- **应检查什么**：输出是 spike/LFP/downstream，还是模型层/算子/probe。
- **常见错误**：把两条路线全部放进第一任务。
- **错误处理**：拆成两个独立任务，只保留共同刺激接口。
- **完成标志**：写出“本轮选择 TA/TB，因为……”。

### 第 4 步：使用层级一或层级二 Prompt

- **应看到什么**：层级一先得到目标解释和最小闭环；层级二先由讨论 Agent 输出已确认内容、默认假设、关键问题和 Prompt 草案，而不是立即执行。
- **应检查什么**：用户决定与默认假设是否分开；较复杂执行 Prompt 是否由讨论过程构建并经过人工确认。
- **常见错误**：要求初学者第一次就手写大量未经核验的库、模型、指标和命令，或让讨论 Agent 直接开始编码。
- **错误处理**：退回一句科学目标，明确“只讨论并替我构建 Prompt，现在不要执行”。
- **完成标志**：层级一形成最小闭环建议；或层级二形成一份经人工确认、包含输入、模型/仿真、中间状态、读取、扰动、测试、图和汇报边界的完整执行 Prompt。

### 第 5 步：让 Agent A 完成项目审计

- **应看到什么**：已有/缺失文件、环境状态、路线、编号、依赖和风险。
- **应检查什么**：Agent A 是否实际打开总纲和项目文件。
- **常见错误**：把建议目录写成已经存在。
- **错误处理**：要求逐项给绝对路径和“存在/不存在/待核验”。
- **完成标志**：审计结果可由文件树和证据复核。

### 第 6 步：人工阅读第一份任务书

- **应看到什么**：单一科学问题、最低 baseline、测试、图、验收和停止条件。
- **应检查什么**：任务是否能在当前硬件完成；是否擅自扩大范围。
- **常见错误**：直接点击执行，不看验收和不能支持的结论。
- **错误处理**：缩小任务、删除非必要模型、补失败条件。
- **完成标志**：人工能准确复述“做什么、为什么、做到什么算结束”。

### 第 7 步：让 Agent B 执行

- **应看到什么**：先环境核验和最小版本，再测试、实验、图和报告。
- **应检查什么**：Agent B 是否严格读取任务书；是否记录失败命令。
- **常见错误**：未通过测试就批量跑实验。
- **错误处理**：停止批量运行，先修复最小测试。
- **完成标志**：每个实际动作都有配置、命令、日志和路径。

### 第 8 步：检查测试和图

- **应看到什么**：PASS/FAIL/NOT RUN 清单，以及真实结果生成的图。
- **应检查什么**：时间轴、单位、seed、对照、变异和重绘来源。
- **常见错误**：只看一张漂亮主图或只看总准确率。
- **错误处理**：打开原始图、失败图、指标表和日志。
- **完成标志**：图与指标、配置和运行记录相互一致。

### 第 9 步：让 Agent A 审核

- **应看到什么**：实际文件、diff/manifest、测试、图和科学解释的独立审核。
- **应检查什么**：审核是否只复述执行报告。
- **常见错误**：代码格式通过就宣布科学任务完成。
- **错误处理**：要求逐项证据矩阵并复核关键指标。
- **完成标志**：得到唯一 `ACCEPT`、`REWORK`、`REDESIGN` 或 `ROLLBACK`。

### 第 10 步：人工判断结论

- **应看到什么**：能支持、不能支持、阴性结果和替代解释。
- **应检查什么**：是否把模型近似当生理事实，把 probe 当显式编码。
- **常见错误**：因为指标提高就自动继续更复杂模型。
- **错误处理**：回答第 14 章十二个问题。
- **完成标志**：人工决定有具体理由、证据和范围。

### 第 11 步：接受、返工、重做或回滚

- **应看到什么**：具体状态、负责者、动作、证据和重新验收条件。
- **应检查什么**：失败记录是否保留；可靠 baseline 是否受保护。
- **常见错误**：用“继续完善”掩盖状态，或覆盖失败 run。
- **错误处理**：按第 15 章选择合法状态并写决策记录。
- **完成标志**：任何人都能知道下一步和停止点。

### 第 12 步：进入下一编号任务

- **应看到什么**：新任务的 `depends_on` 只指向已接受结果。
- **应检查什么**：进入条件是否满足，下一问题是否真的需要。
- **常见错误**：未完成 TA001 就做 TA003，或未完成 TB001 就提出 TB003。
- **错误处理**：回到当前失败任务，或记录 no-go/转向。
- **完成标志**：下一任务有唯一编号、最小闭环和人工确认。

## 18.2 第一次启动的一页核对表

```text

[ ] 第2步：阅读项目总纲
[ ] 第3步：选择TA或TB路线
[ ] 第4步：使用层级一或层级二Prompt

[ ] 第6步：人工阅读第一份任务书
```

# 19. 待确认问题与维护清单

## 19.1 当前项目启动前仍需确认

以下事项不能由本手册替项目作答：

1. 第一项正式任务选择 TA001 还是 TB001；
2. 当前实际可用的操作系统、Python、CPU、GPU、内存和磁盘；
3. 是否使用 Conda、`venv` 或现有环境；
4. Git 是否存在、是否允许使用，以及提交/远端策略；
5. coordination 文件由谁创建、谁有写入和确认权；
6. 统一刺激的采样率、时长、频率和强度范围；
7. TA001 首个主要 decoder 读取 frequency、intensity、AM rate 还是 phase；
8. TA001 先采用自主简化模型还是核验后的历史模型；
9. TB001 的简单 baseline 选择 causal CNN、TCN、GRU 还是其他；
10. TB001 首个代表性预训练模型、模型卡、许可证、中间层接口和资源；
11. causal 与伪流式的 chunk、look-ahead 和延迟定义；
12. 测试阈值、随机种子数、主要指标和 go/no-go 数值；
13. 数据、权重、日志和失败结果的存储与备份位置；
14. 真实语音或环境声的来源和许可证；
15. 两条路线第一次汇合使用哪个共同变量和 decoder。

## 19.2 每次模型或工具升级时重新核验

- 官方代码和模型权重是否仍可获得；
- 许可证是否改变；
- 官方推荐版本和依赖；
- 输入采样率和预处理；
- 是否支持中间层输出；
- 是否真正支持 causal/streaming；
- 是否需要 GPU 或专用 kernel；
- 输出时间分辨率、状态和缓存接口；
- 已知安全、数值或兼容性问题。

无法确认时写“待核验”，不要沿用旧记忆作为当前事实。

## 19.3 手册维护触发条件

出现以下变化应修订本文：

- 项目总纲正式更新；
- TA/TB 编号或依赖规则变化；
- 双 Agent 角色或审核状态变化；
- coordination 文件体系变化；
- Git/无 Git 安全规则变化；
- TA001/TB001 最低交付变化；
- 新的共同刺激 schema 或评价规范被冻结；
- 实际项目暴露了本文未覆盖的高频失败模式。

修订时保留变更理由和日期，不把某一轮临时 workaround 写成长期规范。

## 19.4 最终提醒

对初学者而言，最重要的不是第一次就选到最复杂的模型，而是始终能回答：

```text
我研究的问题是什么？
输入和ground truth是什么？
模型中间发生了什么？
下游怎样读取？
我只改变了什么？
结果是否可重复？
测试和图来自哪里？
当前结论能支持到哪里？
失败证据是否保留？
为什么值得进入下一步？
```

当这些问题都有实际文件、配置、日志、测试和图支持时，项目才从“代码运行”进入“可维护的算法研究”。
